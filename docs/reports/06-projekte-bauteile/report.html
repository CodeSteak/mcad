1 Scope

  • include <file> / use <file> with OpenSCAD semantics: include inserts the statements of the file at its position (definitions, variables, geometry; the last assignment wins, with a warning across the file boundary); use only makes modules and functions visible, which run in their own file (they see that file's variables and its own use libraries, not transitively); own definitions take precedence over used ones, among several use the last one wins. Paths relative to the including file (or absolute). Cycles and missing files are errors at the include/use line.
  • File IDs in source positions: each loaded file occupies its own range of positions (file f from f·224, statement IDs from f·222); diagnostics, hints, handles, spans and text edits thus know their file. The protocol outputs positions local to the file (SrcRange.file, Diagnostic.file, Edit.file, Scene.files); writing back hits the correct file.
  • File resolver: cad-eval reads project files via the trait FileResolver (file system for the CLI, map for session/Wasm). The session receives the files with SetFiles/SetFile. The engine cache is unchanged (keys from the content).
  • Projects in the UI: files as tabs above the editor (separate undo history per file), selectable main file (★), new files, removal; open a folder (File System Access API, saving writes back), otherwise upload and download a ZIP; autosave of the whole project to IndexedDB; example projects in the examples menu. Ctrl+click on the path in include/use opens the file; a double-click on an instance of a module from another file opens that file at the definition; handles write into the file of the literal (also files that are not displayed, one undo step there); face from another file: the status bar names file and line, a click opens it.
  • Multiple parts (open item 2, plan 12.9): named instances at the top level of the main file are parts. Scene with bounding box and volume per part; parts bar with visibility and export STL/3MF/STEP per part, all as ZIP (STL or STEP) or one 3MF with one object per part. STEP (exact B-rep, AP242/AP214) goes through the same writer as the whole model: Engine::export_step is Engine::export_step_nodes of the root, parts are passed with their placement (display_world) via Kernel::transform and Kernel::brep to cad_step::write. CLI: cad export --part name (also .step, --schema), --all-parts -o ordner/ [--format step].
  • Named instances in loops (plan 12 item 2): for (i = [0:3]) k[i]: halter(); → k[2].anker; integer index, visibility as for named instances, snapping writes k[2].ecke. k: … in a loop remains an error.
  • Example project examples/projekt-gehaeuse/: gehaeuse.scad (main file), konstanten.scad (include), lib/teile.scad (use, with screw bosses dom[i]), parts gehaeuse and deckel.

6 Deviations and limitations

  • Search path: only relative to the including file or absolute; no OPENSCADPATH/library folder. Missing files and include cycles are errors (OpenSCAD: warning, the file is skipped).
  • use: variables of a library are evaluated once per evaluation (lazily), not anew on every call as in OpenSCAD; $ variables at the top level of a library apply in its modules. The geometry of used files is not generated.
  • A file included twice (via two include paths) is loaded twice (two file IDs, same path); at most 255 files, at most 16 MiB per file.
  • Snap visibility of a grid/instance named in an included file extends to the end of that file (not into the including file); evaluating k.anker is not affected by this.
  • Parts only in file context; a hidden part inside a boolean operation cannot be hidden separately (the subtree stays whole). Assemblies are open.
  • STEP of several parts in one file: one product (name: part names joined with " + ") with all bodies, no assembly structure per part; a part whose module is an implicit union consists of several bodies (e.g. an enclosure with screw bosses).
  • solidcore is now opt-in (--features solidcore); cad diff-kernels without the feature reports "build with --features solidcore" (exit 2).
  • Module names that are the same in the main file and a library: the context (parameter bar) takes the module of the main file.
