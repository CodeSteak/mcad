1 Task and result

Report 8 measured 0.4–1.1 s for a single cad render, of which the kernel took up to 640 ms; cad watch with a warm cache 24 ms. Every CLI call started with an empty cache. Now a background process cad daemon serve keeps the engine cache across calls: the first computing command starts it, it ends after 15 min without a request, the cache size is limited, and it is off with --no-daemon, CAD_NO_DAEMON=1 or [daemon] enabled = false. Output, exit codes, files and JSON are the same as without the daemon; a second call on the same file takes 34–209 ms instead of 287–1,357 ms.

2 Architecture

cad check|eval|inspect|render|export|outline|measure|set …     (client, one process per call)
  1 cad-ipc: connect("daemon") → hello {proto, build_id, pid}
      no daemon     → start cad daemon serve (setsid, stdin /dev/null, stdout/stderr → daemon.log),
                      wait up to 5 s for hello
      other build ID → stop (graceful, SIGKILL after 3 s), start a new one
      error (no folder, foreign socket, Windows) → silently compute locally
  2 run {argv, cwd, stdin?} ─────────▶  connection thread ── channel ──▶ worker thread (256 MiB stack)
     ◀── accepted, wait (1 s tick)       (per connection)                one Engine<SmlibKernel> for all projects
     ◀── stdout, stderr, exit, files                                     chdir(cwd); Cli::try_parse_from(argv);
  3 write files (atomic for set),                                        run(&cmd) with a session on the engine
    print stdout/stderr, exit code                                       (host.rs: record files, stdin)
                                         monitor thread: idle 15 min, watchdog 60 s, socket present?
daemon.lock (flock, PID + build) · daemon.sock (0600) · daemon.log  in  $CAD_IPC_DIR | $XDG_RUNTIME_DIR/controller-cad | /tmp/controller-cad-<uid>
  • Same code with and without the daemon. The CLI commands run unchanged; three places go through host.rs: load() gets a session via host::new_session (in the daemon on its engine, Session::with_engine; when the command ends, host::Pooled returns the engine), stdin comes from the client, and file writes (render PNG, export, --all-parts folder, set atomic) are recorded in the daemon and executed by the client. Output and exit code are built by the same function finish() in the daemon as locally. If writing fails on the client, it recomputes locally and thus gives the same error message.
  • Same face tags. The engine assigns tags in the order in which it first sees node contents; in an engine that has already computed other models, the numbers differ from those in a fresh process (visible in eval --json: nodes[].tag, tag_nodes). The session therefore numbers tags itself in the order of its jobs – exactly the numbers of a fresh engine – and translates scene and meshes (render colors via this mapping). With its own engine the translation is the identity and costs nothing (browser, desktop).
  • Working directory: before each command the daemon changes to the client's directory (afterwards to /); relative paths, messages and include behave as locally. One worker thread, commands run one after another (SMLib has global state).
  • Exactly one daemon: flock on daemon.lock (new in cad-ipc: LockFile, file removed at the end, inode check against removal by the predecessor). A process that does not get the lock waits up to 10 s and exits as soon as a daemon responds; several simultaneous clients therefore at most start processes that exit again immediately.
  • Version: hello returns protocol and build ID (version + size and modification time of the executable); on mismatch the client stops the old daemon and starts a new one.
  • Watchdog: if a command runs longer than 60 s, the daemon reports "watchdog" to the waiting clients and exits (the hanging kernel call cannot be aborted, as with the engine process of the desktop app). The client repeats the command without the daemon and says so on stderr. After 10 s without a sign of life (wait arrives every second) the client kills the daemon (SIGKILL) and computes itself.
  • Security: only the Unix socket from cad-ipc (user's folder 0700, socket 0600, peer UID), no network; requests only hello, run, status, stop; run only for the eight commands (checked with the CLI parser). The daemon reads files as the same user and writes none.

  • Cache: one LRU of the engine for node results and meshes together (before: 4096 nodes without size, meshes 256 MiB separately), with a byte limit and an entry limit; the newest entry stays even if it alone exceeds the limit. One engine for all projects; the keys are content-based.
  • Projects: per main file (absolute path; stdin per working directory) the daemon remembers the keys its commands touched. With the 9th project, the least recently used one loses its entries unless another held project uses them.
  • RSS: after each request from /proc/self/statm; above start RSS + 1.5 × cache limit the cache is cleared and free memory returned with malloc_trim. The start RSS (about 35–40 MiB: executable, SMLib, Tauri libraries) does not count against the limit, otherwise a small limit would always trigger.
  • Lifetime: exit after 15 min without run (status does not count), after cad daemon stop (waits for running commands), when the socket is removed or replaced (e.g. test folder deleted), after the watchdog; socket and lock file are removed.

Memory estimate

Kernel results are handles in SMLib; only the C++ heap knows their size. Measured with crates/cad-cli/examples/cache_size.rs: evaluate each of the 48 example models with a fresh engine, then drop the engine and count the freed heap bytes (glibc mallinfo2). The breps hold 10–297 KiB per face (median 26 KiB), free-form surfaces and variable fillets the most. The first estimate from the topology (4 KiB + 3 KiB/face + 1 KiB/edge) was too low by a factor of 6. Now: Kernel::shape_bytes for SMLib 8 KiB + 32 KiB per face + 1 KiB per edge (sum over all examples 1.10×, per model 0.13–4.54×) and in the daemon additionally a measurement per node: heap after minus before the evaluation of the node (Engine::set_heap_probe), which captures the new breps of the node including SMLib intermediate data. The estimate per model is thus 1.00–1.55× of what is actually held (median 1.01), never below.

6 Known limitations

  • Unix only (Linux, macOS; peer UID check only on Linux, otherwise the 0700 folder protects). On Windows every command computes by itself, silently.
  • One worker thread: simultaneous CLI calls wait for each other (without the daemon they would run in parallel in separate processes); wait events keep the clients alive.
  • The watchdog also hits a legitimately long command (> 60 s): the daemon exits, the command runs a second time without the daemon. A crash in the kernel (signal) also ends the daemon; the local repetition can crash the same way. The watchdog is tested with an artificial delay (CAD_DAEMON_DEBUG_HANG_MS), not with a real hanging SMLib call.
  • Memory measurement per node only with glibc; allocations of other threads (connections) are counted too. Without glibc the topology estimate applies (per model factor 0.1–4.5). The RSS is checked after each request, not during an evaluation.
  • Differences from the output without the daemon: the additional JSON field daemon; counters and timings (stats.cache_hits, kernel_calls, cached, *_ms, timings, the „Statistik“ line of eval) show what actually happened. On a panic, message and exit code are the same, but the runtime's panic message goes to the log instead of stderr.
  • Build ID from size and modification time of the executable: if two cad binaries alternate (debug and release), they replace each other's daemon (cache lost). An old daemon that is still computing is killed after 3 s; its client then computes itself.
  • The engine's tag table keeps growing (one entry per node content seen); after 2²⁰ tags the daemon replaces the engine together with its cache.
  • cad watch does not use the daemon (own cache in the process); cad set checks the change with a second, kernel-less session without cache (as before).
