3 Findings in detail

F9 – crash with union(fillet) and tangential contact

Examples
tests/alltag/fehler/f09a_absturz_tangentialer_dom.scad, tests/alltag/fehler/f09b_absturz_zapfen_sweep.scad
Cause
In SmFilletExecutive::CreateFilletCorners (SMLib) a corner type is chosen for each vertex of the edges to be filleted. If there is no suitable one (SmFilletCorner::Create returns NULL, "Unimplemented corner case"), the vertex was skipped with continue – but the table m_vVertexCornerMap still held the list of its edges for it (SmTArray<SmEdgeuse>). GetFilletCornerOfVertex later returned this list as SmFilletCorner*; CollectTangentEdgeSequence called virtual methods on it → access to address 0x2f08 (gdb with debug objects, valgrind: "not stack'd, malloc'd or free'd"). In F9a the missing corner type is the tangential contact boss/wall, in F9b the nearly tangential circular edge pin/sweep.
Fix
smlib/patches/0002-fillet-missing-corner.patch: without a corner type the entry is removed and the fillet ends with SM_ERR_INVALID_INPUT, the edge is recorded in SmFilletErrorInfo. The facade translates this into "SMLib cannot blend the corner where these edges meet (faces that touch tangentially there?)" with the edge (red in render --line). In F9a the union already reports the tangential contact (see F8c): boss and wall touch along a line, there is no manifold result. The daemon fallback was no solution: the crash comes from the process itself.

F8 – booleans with torus and rotate_extrude

Examples
tests/alltag/fehler/f08a_union_torus.scad, tests/alltag/fehler/f08b_union_ring_verloren.scad, tests/alltag/fehler/f08c_differenz_torus_tangential.scad
Cause
Not the torus itself but its transformation: the facade called SmBrep::Transform(m, TRUE); with TRUE SMLib derives the model size from the bounding box of the vertices and sets all tolerances (vertices, edges, faces, and those of the global context) from it. A torus and the solid of revolution of a circle have exactly one vertex – bounding box 0, tolerance 0. With tolerance 0 the surface intersection misses every intersection curve: union = both bodies side by side (F8a, 6049.65 mm³ = sum), ring lost (F8b), intersection empty. Verified: the same torus created directly at z = 2 intersects correctly, moved (or only rotated or scaled) it does not; the geometry (B-rep stream) is identical, only the tolerances 1e-5 → 0 differ. F7 (torus as zone selects no edge) has the same cause.
Fix
apply_matrix transforms with Transform(m, FALSE): rigid motions leave the tolerances unchanged; with scaling the facade sets them from the whole (loose) bounding box of the body, the context stays untouched. F8c: the torus touches top and bottom face tangentially along two circles; the result is not manifold (SMLib returns it with the correct volume 5260.36 mm³, but not closed; measure showed 0). The boolean check no longer accepts a non-closed result of two closed bodies as a "last resort" but reports "the result is not a closed solid: the operands touch tangentially or along an edge there (let them overlap a little or keep a gap)". If the bodies only touch (interiors do not overlap), a − b = a and a ∩ b = empty apply instead of a non-manifold body.

F5 – chamfer via zone on the filleted box: volume 0, status ok

Examples
tests/alltag/fehler/f05_fase_volumen_null.scad
Cause
SMLib returns SM_SUCCESS and an open shell: the top face is missing. The reason is the geometry: at the corners the wall between outer radius 6 and the sharp inner corner is only 6 − 3√2 ≈ 1.76 mm thick; the outer chamfer takes 0.8 mm, the inner chamfer at the sharp corner 0.8·√2 ≈ 1.13 mm – the chamfers intersect, the top face falls apart. Re-measured: chamfer(0.7) works, chamfer(0.75) does not (computed limit 0.73). Chamfers of the outer and of the inner edge each work on their own.
Fix
The facade checks every result of a fillet/chamfer (blend_core): closed shell if the input was closed; volume > 0 and volume change at most as large as a fillet of this size can cause near the edges (20 r² per mm of edge length + 10 r³ per edge + 2 %). Violated → "SMLib returned a body that is not closed (faces missing): the blends of neighbouring edges collide, size too large for the wall between them?" with the edges. In addition: if the selection fails as a whole and splits into separate edge chains (without a shared vertex), the chains are filleted one after another (edges found again in the intermediate body via their geometry) – futile here because the chamfers really collide, but helpful where SMLib only fails on the combination.

F1 – sweep with symmetric spline profile "not centred"

Examples
tests/alltag/fehler/f01_sweep_spline_profil.scad
Cause
SMLib (CreateCurveSweep, bMoveProfileCenterToPath) places the center of the bounding box of the profile curves on the path. CalculateBoundingBox of a B-spline curve is the bounding box of its control points: for the closed interpolating spline through (5,0) (0,3) (−5,0) (0,−3) x −15…5, although the curve itself is symmetric (sampled ±5, ±3.08). The facade rejected every such "off-center" profile on a curved path.
Fix
smlib/patches/0003-sweep-profile-reference-point.patch: SmSweepOptions gets bUseProfileRefPoint/sProfileRefPoint; the facade specifies the origin of the profile frame (path start). Any profile, including deliberately off-center ones (circle at (0, 4)), thus follows the path with its origin; the shift after the sweep on straight paths is no longer needed. Only the mitered variant for planar polyline paths lacks the option (the message names the workaround: spline path).

4 Display and CLI (S1–S4)

S1 – profile grid with rotate_extrude

Cause: a 2D grid (x = radius, y = height) is drawn in the coordinate system of its module, i.e. in the xy plane; after rotate_extrude the profile lies in the xz plane. Fix (CLI): cad render --show grids checks the references of each grid (Scene.refs): if all lie in 2D nodes below the same rotate_extrude, the grid is drawn in its profile plane (frame RE · Rx(90°) · RE⁻¹ · N · frame_module) and a note is printed. Grids with references outside (or via variables) stay as they are.

UI (not changed, web/): the 3D view draws grids from Scene.grids[].frame. For the same fix it would need either the rule above (references from Scene.refs → 2D nodes → op_info.kind == "rotate_extrude") or, better, a frame that the scene supplies per grid (Grid.display_frame, computed in cad-session by the same rule). For dragging/snapping to grid points the handles would have to be mapped into the profile plane as well.

S3 – outline and visibility

cad outline listed instances named in the body of a module (dom[0] … in pi_platte) under the file's „Benannte Instanzen“ (named instances) and their anchors as file anchors. Now: a separate section „Benannte Instanzen in Modulen (nur dort sichtbar)“ (named instances in modules, visible only there) grouped by module; in the JSON scope: "file" | "module" and in_module; anchors only of the file instances. That measure --between dom[0].oben … still works in file context is language semantics (cad-eval) and remains a proposal: resolve such names only via the instance chain (platte.dom[0].oben) or with a warning.

S4 – section caps and grid labels

A model made of parts was drawn in section as one mesh of the root: the caps of touching parts merged. Now, as soon as the parts make up the whole model, it is drawn per part: its own cap with alternating hatching and its own section contour. Grid labels: rows of indexed planes (rippe[0] … rippe[7]) get one label g.rippe[0..7]; 3 px remain between labels (before, they could touch directly).

S2 – plane names as values, anchor lists (assessment only)

  • Plane names as values (g[i % 2 == 0 ? loch_l : loch_r, …]): the names in g[…] are selectors today, not expressions; the workaround via numbers (g.loch_l) loses the grid binding (snap, dragging). Proposal: a value type "plane" (g.loch_l still yields the number, but plane(g.loch_l) or a selector expression g[sel(i % 2 == 0 ? "loch_l" : "loch_r"), …]) that g[…] accepts; this keeps the origin for handles. Effort medium (cad-eval: selector evaluation, drag write-back only for literal selectors).
  • Anchor lists (anchor loch[i] = … in a loop): fits the existing indexing of instances (k[i]) and planes (rippe[i]). Proposal: the same rule as for planes (name + index, outside k.loch[2]), snap targets per element. Effort low to medium.
  • Grid-local coordinates for profiles in rotated planes (S1): a grid with its own frame (grid p in xz { … }) would also solve S1 in the language.

Cause: after the kernel run the session computes the volume of each part (part list of the scene, part_volumes); after the mass properties (1e-4), sc_mass_props additionally called SmApiBrepComputeVolume(…, 1e-8). The accuracy 1e-8 costs about 11 s for the swept hooks via adaptive Runge–Kutta integration per face (SmFace::ComputePreciseProperties). Measured relative volume error: 1e-6 → ≤ 4.4e-6, 1e-7 → ≤ 1.1e-7, 1e-8 → ≤ 1.5e-8 (sphere, torus, cone). Fix: 1e-6 (part volumes are displayed to 0.1 mm³; checks use 0.1 %).
